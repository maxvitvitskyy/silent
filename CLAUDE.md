# SILENT — інструкції для роботи в цьому репозиторії

Статичний сайт silent-disco сервісу SILENT (Київ, виїзд по Україні). Ніякого
бекенду й білд-кроку немає — чистий HTML/CSS/JS, GitHub Pages, власний домен.

- Робоча копія: `/Users/maxvitvitskyy/SILENT_WEB`.
- Репозиторій: https://github.com/maxvitvitskyy/silent (публічний, гілка `main`).
- Живий сайт: **https://silent.org.ua** (кастомний домен;
  `maxvitvitskyy.github.io/silent/` віддає 301 на нього).
- Українська версія (`index.html` і решта) — єдине джерело правди. Англійська
  (`en/`) генерується скриптом, руками не редагується.

## На початку кожної сесії

Прочитай **`PROGRESS.md`** (у корені, не в git) — там стан проєкту на момент
останньої паузи: що щойно зроблено, що відкрито, на що чекаємо від власника.
Якщо файла нема — почни з `git log --oneline -20`, коміти тут із детальними
поясненнями «чому», не лише «що».

Для дизайн-роботи (правки вигляду, нові блоки, polish) — спершу скіл
`impeccable`, він сам підвантажить `PRODUCT.md` (локальний, не в git: там
аудиторії, позиціювання, і головне — тверді обмеження: не вигадувати відгуки,
не згадувати документи/рахунки, формулювання гарантії не розширювати).

## Пастка, на яку вже наступали: кеш версій

**Після будь-якої правки `assets/site.css` або `assets/site.js` обовʼязково
запустити:**

```bash
python3 tools/build_en.py
```

Скрипт проставляє `?v=<хеш>` у посиланнях на ці файли в усіх HTML. Без цього
кроку браузер (і локальний дев-сервер, і сам живий сайт) тримає стару
закешовану версію файлу під тим самим URL — навіть після `location.reload()`
чи нової навігації. Симптом: правка є на диску, `curl` її бачить, а сторінка
в браузері поводиться так, ніби нічого не змінилось. Перевіряти актуальну
версію: `[...document.styleSheets].map(s=>s.href)` / `document.querySelector('script[src*="site.js"]').src`
у консолі сторінки — хеш має збігатись із щойно згенерованим.

Той самий скрипт синхронізує картки сценаріїв між сторінками (з `index.html`
у `experiences/*`) і збирає `en/`. Правка тексту в `index.html` без наступного
запуску `build_en.py` розійдеться з англійською версією й дочірніми сторінками.

## Деплой

1. `git add` / `git commit` / `git push origin main` — **тільки коли користувач
   прямо про це просить**, це публікує зміни назовні.
2. Дочекатись збірки:
   ```bash
   gh api repos/maxvitvitskyy/silent/pages/builds/latest --jq '"\(.status) \(.commit[0:7])"'
   ```
   Повторювати, поки `status` не стане `built` для щойно запушеного коміту.
3. Звірити на живому сайті. **Живий сайт теж кешує** — якщо сторінка вже була
   відкрита в цій сесії браузера раніше, `navigate` покаже старий стан. Робити
   `location.reload(true)` і лише тоді перевіряти.

## Структура

- `assets/site.css`, `assets/site.js` — увесь сайт, один спільний файл кожного.
  Коментарі в CSS/JS навмисно докладні й пояснюють «чому», не мінімізувати.
- `experiences/corporate/index.html` — перша з серії сторінок-досвідів,
  наступні (весілля, конференції…) мають копіювати її структуру.
- `experiences/index.html` — сторінка-каталог усіх форматів, із фільтром тем.
- `tools/build_en.py` — генерує `en/`, синхронізує картки сценаріїв між
  сторінками, стемпить версії активів. Читай коментарі на початку файлу —
  там пояснено, які маркери (`UC-STRIP`, `UC-FILTER`, `UC-GRID`) що роблять.
- Зображення-джерела (необроблені PNG з Firefly/ChatGPT, 20–40 МБ кожне) не
  повинні лишатись у теках, які роздає сайт (`images/`, `experiences/*/`) —
  вони або гітігноряться (перевір `.gitignore`), або їх треба прибирати після
  використання.

## Робочі звички

- Перед батчем правок UI дивитись і на десктоп, і на мобільний (390px) — сайт
  адаптивний, і половина минулих багів була помітна лише на одній ширині.
- `read_console_messages` у цій сесії інколи повертає застарілий буфер, що
  накопичився з попередніх навігацій у тій самій вкладці. Якщо результат
  сумнівний — закрити вкладку (`tabs_close`) і відкрити наново (`preview_start`)
  перед тим, як довіряти показникам консолі.
